Synthetic eval data is test cases written by a model instead of a person, then filtered until they are worth keeping. You give the generator a description of the task, a handful of real examples and a list of ways the system tends to fail, and it produces hundreds of inputs with expected answers or checkable properties. The point is to get a [golden dataset](./golden-dataset.md) large enough to measure with when real labelled examples are rare, confidential or slow to collect.

The risk is that the generated set is easier than the real world. One team built a 2,000-case synthetic set for a support assistant in a day and celebrated a 95 percent pass rate. When they finally sampled 100 real tickets and graded them by hand, the pass rate was 30 percent. The generator had written tidy, single-question tickets in full sentences. Real tickets were two paragraphs of history, three questions at once, and a screenshot described in words. The synthetic set measured the system's ability to handle the generator's idea of a ticket.

Filtering is where most of the value is. Drop cases the model answers correctly without any context, because they measure nothing. Remove near-duplicates with [embeddings](./embeddings.md), since a generator asked for 200 variations will quietly produce 40 rewordings of the same case. Check expected answers with a second model or a rule, and send a random sample of 30 to a human grader before you trust the whole set. A set where a quarter of the sampled cases are wrong is not an eval, it is noise with a decimal point.

| Generation approach | Strength | Weakness |
| --- | --- | --- |
| Free generation from a task description | Fast, large volume | Easy, generic, repetitive |
| Variations of real seed cases | Realistic structure | Inherits gaps in the seeds |
| Targeted at a [failure taxonomy](./failure-taxonomy.md) | Stresses the modes that matter | Needs prior [error analysis](./error-analysis.md) |

Same-model bias is a quieter problem. If the model that writes the cases is the one being tested, or the one acting as [LLM-as-judge](./llm-as-judge.md), it shares the same blind spots and will neither write the inputs that break it nor notice when they do. Use a different model family for generation where you can, and keep a small real holdout that the synthetic set must agree with before you report its numbers in [evals](./evals.md).

Treat synthetic data as a way to extend real data, not replace it. Seed the generator with real structure, aim it at known failure modes, filter hard, and write the grading criteria with the same care as any [rubric](./rubric-design.md). The synthetic set earns trust only when its scores move in the same direction as the real holdout.

_Usage:_

- "The synthetic set passes at 95 percent and real tickets fail at 30. The set is too easy."
- "Seed the generator with twenty real cases, then filter anything the model gets right with no context."
- "Hand-grade thirty of them before anyone quotes that pass rate in a slide."
